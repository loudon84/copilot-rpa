AutoTask 产品规划与系统架构设计文档
v1.0 Architecture Baseline
面向对象：产品经理、前端、后端、RPA 引擎、测试、实施同事。
设计目标：高可扩展、低耦合、权限清晰、任务闭环可追溯。
当前技术栈：Electron + React 客户端；nodeskclaw-backend + nodeskclaw-task；RPA 引擎使用 Playwright + CDP。
---
1. 产品定位
AutoTask Studio 是面向供应链部门的 客户 / 供应商 Portal 自动化任务工作台。
它不是单纯的 RPA 工具，而是一个围绕客户 SRM、供应商 Portal、业务流程模板、任务状态、人工介入、消息通知和 RPA 执行结果进行协同管理的 C/S 产品。
核心定位：
AutoTask Studio Client
  = 供应链用户工作台
  = Portal 账号管理台
  = 任务流程模板管理台
  = 任务消息与状态查看台
  = Web 工作区

nodeskclaw-backend
  = 用户登录
  = 权限治理
  = 组织 / 角色 / 用户 / 资源授权

nodeskclaw-task
  = AutoTask 业务数据接口
  = 任务分发
  = 消息通知
  = MCP 能力暴露
  = 任务状态与运行记录管理

RPA Engine
  = Playwright + CDP 执行器
  = Portal 自动化脚本运行时
  = 运行日志 / 截图 / Trace / Artifact 生成器
当前 MVP 已具备工作台、任务列表、Web 工作区、任务记录、管理中心等基础页面，符合原型阶段的信息架构；原始 Mock UI 中也已经明确包含工作台、自动化任务、流程模板、RPA 组件库、客户 SRM、运行监控、证据中心、系统设置等模块。

2. 架构设计原则
2.1 高扩展原则
后续产品会不断接入新的客户 SRM、供应商 Portal、ERP 编码、流程模板、RPA 脚本、通知渠道和智能体能力，因此架构必须避免硬编码。
设计原则：
1. Portal 账号是核心资源，不把客户 / 供应商 Portal 写死到代码里。
2. 工作流程模板与 RPA 执行脚本解耦。
3. 任务状态由 nodeskclaw-task 统一管理。
4. RPA 引擎通过接口接入，不反向侵入业务系统。
5. MCP 只暴露稳定业务能力，不暴露内部实现细节。
6. 权限模型面向资源授权，而不是面向页面授权。
7. Artifact、RunEvent、AuditLog 独立建模，便于后续审计和追溯。
2.2 低耦合原则
系统按职责拆分：
客户端只做工作台与 Web 操作。
nodeskclaw-backend 只做身份、组织、权限。
nodeskclaw-task 只做 AutoTask 业务编排、任务、消息、状态。
RPA Engine 只做执行。
ERP 只作为主数据映射来源，不直接驱动 UI 状态。
这与前面已确认的 v0.4 方向一致：Desktop 使用 WebContentsView 作为用户 Web 工作区，RPA Worker 继续承担 Browser Manager、Step Executor、SRM Adapter、Screenshot、Trace、Error Handler 等自动化能力。

4. 边界上下文设计
采用类似 DDD 的边界上下文划分，避免模块相互侵入。
4.1 Identity & Permission Context
归属：nodeskclaw-backend
职责：
用户登录
组织架构
角色
权限策略
资源访问授权
Token 签发
审计主体识别
不负责：
不保存 Portal 业务配置
不保存任务模板
不保存 RPA 运行状态
---
4.2 Portal Account Context
归属：nodeskclaw-task
职责：
客户 SRM Portal 账号管理
供应商 Portal 账号管理
ERP 客户编码 / 供应商编码绑定
Portal URL + 登录账号唯一性校验
凭证引用
用户访问权限
启用 / 禁用
本地 Web 打开配置
服务器 RPA Profile 引用
这是 AutoTask 的核心资源上下文。
---
4.3 Workflow Template Context
归属：nodeskclaw-task
职责：
维护业务流程模板
维护前端可读步骤文档
维护输入参数定义
维护启用 / 关闭状态
维护模板版本
绑定 Portal Account
绑定 RPA Flow
重要拆分：
业务流程模板 ≠ RPA 脚本
产品经理和业务用户维护的是“业务流程说明和步骤文档”；RPA 工程师维护的是“RPA 可执行流程”。二者通过 WorkflowBinding 绑定。
---
4.4 Task Context
归属：nodeskclaw-task
职责：
创建任务
分发任务
跟踪任务状态
保存任务消息
处理人工动作
接收 RPA 回调
生成运行记录
触发通知
---
4.5 RPA Runtime Context
归属：RPA Engine
职责：
运行 Playwright + CDP
管理浏览器上下文
执行具体动作
处理下载 / 上传
生成截图 / Trace
返回事件
返回错误
生成 WAITING_HUMAN
原有设计中 RPA Worker 已经被定义为负责浏览器、步骤执行、截图、Trace、下载文件、异常处理和运行事件上报的执行层。

5. 核心资源模型
5.1 PortalAccount
统一抽象客户 SRM 和供应商 Portal。
interface PortalAccount {
  id: string

  tenantId: string
  entityType: 'CUSTOMER' | 'SUPPLIER'

  erpEntityCode: string
  erpEntityName: string

  portalName: string
  portalUrl: string

  loginAccount: string
  credentialRef: string

  clientOpenMode: 'webcontents' | 'system_browser'
  clientSessionPartition: string

  rpaProfileId?: string

  status: 'ENABLED' | 'DISABLED'
  ownerDeptId?: string

  createdBy: string
  createdAt: string
  updatedAt: string
}
唯一约束：
tenantId + entityType + portalUrl + loginAccount 唯一
业务强约束：
客户 Portal 必须登记客户 ERP 编码。
供应商 Portal 必须登记供应商 ERP 编码。
portalUrl + loginAccount 不能重复。
账号密码不能明文返回给客户端。

5.2 PortalAccessGrant
用于控制哪些用户可以查看或使用该 Portal 账号。
interface PortalAccessGrant {
  id: string
  portalAccountId: string

  subjectType: 'USER' | 'ROLE' | 'DEPARTMENT'
  subjectId: string

  permissions: Array<
    | 'PORTAL_VIEW'
    | 'PORTAL_EDIT'
    | 'PORTAL_OPEN_WEB'
    | 'PORTAL_USE_CREDENTIAL'
    | 'PORTAL_MANAGE_PERMISSION'
    | 'PORTAL_BIND_WORKFLOW'
    | 'PORTAL_VIEW_TASKS'
  >

  grantedBy: string
  grantedAt: string
}
权限解释：
PORTAL_VIEW
  可查看 Portal 基础信息。

PORTAL_OPEN_WEB
  可在 AutoTask Web 工作区打开该 Portal。

PORTAL_USE_CREDENTIAL
  可触发使用凭证的 RPA 任务，但不能看到明文密码。

PORTAL_EDIT
  可维护 URL、账号、ERP 编码等配置。

PORTAL_MANAGE_PERMISSION
  可授权其他用户访问该 Portal 账号。

PORTAL_BIND_WORKFLOW
  可绑定流程模板。

PORTAL_VIEW_TASKS
  可查看该 Portal 相关任务。

6. 客户 / 供应商 Portal 设计
6.1 客户 SRM Portal
业务规则：
1. 必须登记 ERP 客户编码。
2. portalUrl + loginAccount 在同租户内唯一。
3. 可配置哪些用户 / 角色 / 部门可查看该账号。
4. 用户可被授权打开 Web 工作区。
5. 用户可被授权使用该账号触发 RPA，但不能查看明文密码。
6. 一个客户账号可绑定多个工作流程。
6.2 供应商 Portal
业务规则：
1. 必须登记 ERP 供应商编码。
2. portalUrl + loginAccount 在同租户内唯一。
3. 权限模型与客户 Portal 一致。
4. 一个供应商账号可绑定多个工作流程。
6.3 Portal 账号与 ERP 的关系
ERP 是主数据来源。
AutoTask 保存 ERP 编码作为业务映射键。
AutoTask 不替代 ERP 客户 / 供应商主数据。
建议后续与 ERP 对接时增加：
ERP 客户编码校验
ERP 供应商编码校验
ERP 名称同步
ERP 状态同步

7. 任务流程模板设计
7.1 双层模板模型
为避免业务模板与 RPA 实现耦合，设计为两层：
Business Workflow Template
  产品 / 业务可维护
  描述业务步骤
  描述输入参数
  描述注意事项
  控制启用 / 关闭

RPA Flow Binding
  RPA 工程师维护
  绑定具体 Playwright/CDP 执行流程
  绑定 selector、脚本、超时、重试策略
7.2 业务模板示例
{
  "name": "客户 SRM 获取采购订单",
  "entityType": "CUSTOMER",

      "stepNo": 1,
      "title": "登录客户 SRM",
      "description": "使用已授权账号进入客户 SRM。"
    },
    {
      "stepNo": 2,
      "title": "搜索采购订单",

    },
    {
      "stepNo": 3,
      "title": "下载订单附件",
      "description": "下载 PO、合同或订单确认文件。"
    }
  ]
}

8. 任务生命周期
8.1 标准自动化流程
用户创建任务
  ↓
nodeskclaw-task 校验权限
  ↓
校验 PortalAccount
  ↓
校验 WorkflowBinding
  ↓
任务进入 READY
  ↓
任务分发到 RPA Engine
  ↓
RPA Engine 执行 Playwright/CDP
  ↓
RPA Engine 上报 RunEvent
  ↓
nodeskclaw-task 更新任务状态
  ↓
任务完成 / 失败 / 等待人工
8.2 人工介入流程
本产品只支持类型 A 人工介入：
RPA Engine 或业务规则生成 WAITING_HUMAN
  ↓
nodeskclaw-task 创建 HumanAction
  ↓
客户端任务列表显示 待人工
  ↓
用户点击【快速打开】
  ↓
Electron WebContentsView 打开 targetUrl
  ↓
任务变为 HUMAN_OPERATING
  ↓
用户在 Portal 页面完成业务动作
  ↓
用户点击【确认已完成】
  ↓
任务变为 SUCCESS_MANUAL
不做：
不恢复服务器 Playwright 原会话
不要求同一个浏览器上下文继续执行

10.2 权限模式
建议采用 RBAC + Resource ACL 混合模型。
RBAC
  控制用户是否有模块访问能力，例如是否能进入 Portal 管理、流程模板管理。

Resource ACL
  控制用户是否能查看某个客户 / 供应商账号。
示例：
供应链主管
  可以查看部门下所有客户 / 供应商 Portal 账号。

业务员 A
  只能查看被授权的客户 A、客户 B Portal 账号。

RPA 工程师
  可以维护 WorkflowBinding，但不能查看业务凭证明文。

系统管理员
  可以管理用户、角色、授权策略。

12. MCP 能力设计
MCP 不直接暴露数据库，也不暴露 RPA 内部细节，只暴露稳定业务工具。
建议 MCP tools：
autotask.portal.search
autotask.portal.get
autotask.workflow.list
autotask.task.create
autotask.task.get_status
autotask.task.list_messages
autotask.human_action.get
autotask.human_action.confirm
autotask.artifact.list
示例：
{
  "tool": "autotask.task.create",
  "input": {
    "portalAccountId": "portal_acc_001",
    "workflowTemplateId": "wf_fetch_po",
    "input": {
      "poNo": "PO-20260703-001"
    }
  }
}
设计原则：
MCP 调用必须经过 nodeskclaw-backend 权限校验。
MCP 不允许绕过 PortalAccessGrant。
MCP 创建任务后仍进入标准任务状态机。
MCP 不直接调用 Playwright。

15. 权限与安全设计
15.1 Portal 账号权限
必须做到：
1. 未授权用户不能看到 Portal 账号。
2. 未授权用户不能打开 Portal Web。
3. 未授权用户不能使用该账号创建任务。
4. 密码永远不明文返回客户端。
5. 使用凭证触发 RPA 必须有 PORTAL_USE_CREDENTIAL 权限。
6. 所有查看、打开、创建任务、确认人工完成都写 AuditLog。
15.2 凭证安全
credentialRef 只保存引用。
真实密码进入加密凭证库。
客户端只显示账号和脱敏信息。
RPA Engine 通过受控 API 获取临时凭证。
凭证使用必须记录审计。
15.3 Web 工作区安全
WebContentsView 不注入业务脚本。
客户 Portal 不暴露 Preload API。
禁止 file://、javascript:、data: 等高风险 URL。
Portal URL 由后端配置或校验。
支持外部浏览器兜底打开。
15.4 CDP 安全
CDP 只在 RPA Engine 内部开放。
不把 CDP endpoint 暴露给客户端。
RPA 浏览器上下文按 PortalAccount / Worker 隔离。

19. 架构确认结论
最终推荐架构：
AutoTask Client
  Electron + React
  面向供应链用户
  管 Portal、流程模板、任务消息、任务状态、Web 工作区

nodeskclaw-backend
  统一登录
  用户 / 角色 / 组织 / 权限治理
  资源级授权

nodeskclaw-task
  AutoTask 业务中心
  PortalAccount
  WorkflowTemplate
  WorkflowBinding
  Task
  TaskMessage
  HumanAction
  RunEvent
  Artifact
  MCP

RPA Engine
  Playwright + CDP
  通过标准接口接收任务
  通过 RunEvent 回调状态
  不直接耦合客户端
这套架构的关键价值是：
1. 客户端、任务中心、权限中心、RPA 引擎边界清晰。
2. Portal 账号作为核心资源，可做细粒度权限控制。
3. 业务流程模板与 RPA 执行脚本解耦。
4. RPA 引擎可独立替换和横向扩展。
5. MCP 只暴露业务能力，不破坏内部架构。
6. 后续接 ERP、消息通知、智能体、更多 RPA 引擎时不需要重构主干。
